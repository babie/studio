# 12. ADR は Michael Nygard 形式・`docs/adr/` 配下で管理する

## ステータス

Accepted

決定日: 2026-05-12

## コンテキスト

このプロジェクトは個人開発者によるツールとはいえ、設計判断の経緯を後から思い出せる形で残しておく必要がある。理由は次のとおり:

- backend 切替・workspace 戦略・プロトコル選定など、Phase 1 で凍結した判断が複数あり、CLAUDE.md にメモするだけでは「なぜそう決めたか」が拾いにくい
- 将来 Milestone 3 以降で state 別 backend 切替や `apps/conductor` 移行などの大きな変更を入れる際、過去判断を覆す根拠を明示したい
- Claude Code との協働で開発を進める都合上、各判断が独立ファイルとして引用しやすい形になっている方が文脈の取り回しが楽

ADR の形式には複数の流派がある:

1. **Michael Nygard 形式 (2011)**: `# タイトル / ステータス / コンテキスト / 決定 / 結果` の 4 セクション。最古参・最軽量
2. **MADR (Markdown Any Decision Records)**: 選択肢比較や related decisions のセクションを持つ。やや構造的
3. **独自形式**: プロジェクトごとに自由設計

本プロジェクトは「事後ドキュメント化」が中心で、選択肢比較というより「なぜそうしたか」を残したい用途。重量級の形式は不要。

## 決定

ADR は以下の規約で管理する:

- **置き場所**: `docs/adr/`
- **形式**: Michael Nygard 形式の日本語版（テンプレートは [`0000-template.md`](0000-template.md)）
- **ファイル名**: `NNNN-kebab-case-title.md`（4 桁ゼロパディング、英数 kebab-case）
- **本文中の参照記法**: `ADR-NNNN`（例: `ADR-0001`）
- **索引**: [`docs/adr/README.md`](README.md) にステータス付き一覧を維持する
- **更新時の運用**:
  - 既存判断を覆す場合は新規 ADR を起票し、旧 ADR のステータスを `Superseded by ADR-NNNN` に書き換える
  - 軽微な修正（誤字・補足）は既存 ADR をそのまま編集してよい
  - 判断の本質が変わる修正は新規 ADR を起こす

## 結果

- **良い影響**:
  - 過去判断と現在判断が同じ書式で並ぶため、Claude Code や他のレビュアーが文脈を拾いやすい
  - ファイル名と参照記法を分離（ファイル名は `0001-xxx.md`、参照は `ADR-0001`）したことで、リネームコストが小さい
  - 4 セクションだけのテンプレートなので書く心理的ハードルが低い
- **悪い影響 / トレードオフ**:
  - 選択肢比較や代替案の検討を明示するセクションがないため、必要な ADR では本文に書き下す必要がある
  - 既存の `docs/architecture.md` や CLAUDE.md と一部内容が重複する（ADR は「決定の経緯」、他は「現在の状態」と役割を分ける運用が必要）
- **影響範囲**: `docs/adr/` 配下の運用、今後の設計判断のドキュメント化手順
