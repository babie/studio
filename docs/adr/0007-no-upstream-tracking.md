# 7. 本家 openai/symphony への追従を放棄する

## ステータス

Accepted

決定日: 2026-05-10

## コンテキスト

`concert` は `openai/symphony` のフォークとして始まった。フォーク後の運用方針として典型的な選択肢は:

1. **本家追従**: 本家を upstream として常に rebase / merge し、独自変更は最小に抑える
2. **完全独立**: 本家との同期を諦め、独自に進化させる

本家追従の場合、Codex 専用設計を温存しつつ Claude 対応を別レイヤで載せる必要があり、Codex 前提の内部構造が残ったままになる。本プロジェクトはむしろ Symphony の内部設計に踏み込んで改造する（state 別 backend 切替、claude-app-server との疎通、Elixir → TypeScript 移行）ことを想定しており、本家と整合させるコストが今後ずっと付きまとう。

加えて、本プロジェクトは特定の開発スタイルに最適化したツールという位置付けであり、汎用のオーケストレーターを目指してはいない。本家と分岐したまま独自進化する方が目的と合う。

## 決定

`openai/symphony` への追従は行わない。

- 本家リポジトリを upstream として登録しない
- 本家の新機能を取り込む必要が出たら都度判断する（必要な時にチェリーピックする選択肢は残すが、自動追従はしない）
- 本家との差分を最小化する努力は行わない。必要な改造は遠慮なく入れる
- `apps/symphony` 内のリブランディング（Elixir モジュール名の置換等）は行わない。`Symphony.*` namespace のまま運用する

## 結果

- **良い影響**:
  - Symphony の内部設計に踏み込んだ改造ができ、Claude 対応や TypeScript 移行が自由に進められる
  - 本家変更への追従コストがゼロ
  - コミットメッセージや README で本家との整合性を気にする必要がない
- **悪い影響 / トレードオフ**:
  - 本家のバグ修正や新機能は手動で取り込まない限り反映されない
  - ライセンス上の責務（Apache-2.0 の派生物表示等）は引き続き果たす必要がある
  - 「本家との互換性」を前提とするユースケースには応えにくくなる
- **影響範囲**: リポジトリ運用方針、コミット規約、`apps/symphony` の進化方向
